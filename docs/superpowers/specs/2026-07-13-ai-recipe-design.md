# AI 食谱推荐设计

## 1. 目标

将用户端 AI 食谱页面从“生成一段推荐文本”升级为可执行的整日三餐计划：AI 只负责在平台真实可售的菜品候选池中进行搭配，后端负责候选池过滤、营养计算、库存校验和购物车写入。

第一版范围：

- 生成早餐、午餐、晚餐的整日食谱。
- 使用用户健康档案和本次饮食限制作为推荐条件。
- 返回真实菜品 ID、份量、价格和营养数据。
- 支持替换单道菜，并即时重新计算营养汇总。
- 支持按商家拆分加入购物车，避免跨商家订单冲突。

不在第一版范围内：

- AI 自由对话。
- AI 直接生成平台不存在的菜品。
- 自动创建跨商家订单。
- 保存历史食谱和周期性订阅。

## 2. 用户体验

页面分为三个区域：

### 条件区

展示当前健康目标和每日营养目标，并提供本次生成条件：

- 餐次，默认整日三餐；
- 饮食限制，例如低糖、低脂或忌口；
- 重新生成。

用户未填写健康档案时，页面明确提示去完善档案，并提供跳转入口，不展示空营养值。

### 食谱区

按早餐、午餐、晚餐分组，每餐显示菜品行。每道菜包含：

- 菜品图片、名称和所属商家；
- 推荐份量和数量；
- 热量、蛋白质、脂肪、碳水；
- 替换菜品；
- 加入购物车。

替换时只展示满足相同餐次、在售、有库存且通过饮食限制过滤的候选菜品。替换后仅更新当前菜品和营养汇总，不重新覆盖用户已确认的其他菜品。

### 营养汇总区

展示目标值、推荐值和差值：

- 热量；
- 蛋白质；
- 脂肪；
- 碳水。

当推荐值超过或低于目标范围时，使用文字和颜色提示，不使用“健康/不健康”的绝对判断。

## 3. 数据流和边界

```text
用户健康档案 + 本次限制
        |
        v
后端筛选真实菜品候选池
        |
        v
AI 根据候选菜品 ID 和营养数据进行三餐搭配
        |
        v
后端校验 AI 返回的 ID、份量和库存
        |
        v
后端计算汇总 -> 前端展示
        |
        +--> 替换菜品 -> 重新校验并计算
        +--> 加入购物车 -> 按商家拆分购物车项
```

AI 返回的结果不能成为价格、营养和库存的权威来源。后端必须根据菜品 ID 重新查询数据库，并以数据库中的当前数据覆盖 AI 的展示数据。

候选池至少过滤：

- 菜品状态为在售；
- 所属商家状态正常；
- 库存满足推荐数量；
- 菜品不命中用户过敏和明确忌口；
- 菜品有可用营养数据。

如果候选池不足，接口返回可理解的部分推荐结果和缺少餐次，不返回虚构菜品。

## 4. 接口设计

统一使用 `POST /api/ai/recommend`。

请求：

```json
{
  "mealType": "all",
  "dietaryRestrictions": "低糖，不吃海鲜"
}
```

响应：

```json
{
  "success": true,
  "dailyCalories": 2200,
  "proteinGrams": 130,
  "fatGrams": 70,
  "carbsGrams": 260,
  "summary": {
    "calories": 1980,
    "protein": 124,
    "fat": 62,
    "carbs": 235
  },
  "meals": [
    {
      "mealType": "breakfast",
      "items": [
        {
          "dishId": 12,
          "dishName": "全麦鸡胸三明治",
          "merchantId": 3,
          "merchantName": "示例商家",
          "quantity": 1,
          "calories": 380,
          "protein": 28,
          "fat": 12,
          "carbs": 42,
          "available": true
        }
      ]
    }
  ],
  "advice": "..."
}
```

替换接口接收当前食谱标识、原菜品 ID 和新菜品 ID。后端校验新菜品是否属于当前候选池，校验通过后返回更新后的整日食谱或最新营养汇总。

加入购物车不直接把整日食谱当作一个购物车项。系统按商家拆分菜品：前端明确提示用户将生成多个商家的购物车分组，结算时每个商家单独填写留言、地址和订单。

## 5. 错误处理

- 未登录：跳转登录或显示登录提示。
- 健康档案缺失：提示完善档案，并保留用户已输入的饮食限制。
- AI 服务不可用：提供基于规则和候选池的兜底推荐，或说明暂时无法生成，不展示伪造结果。
- 菜品刚刚下架或库存变化：从结果中标记不可用，提供替换入口，不允许加入购物车。
- 单个商家加入失败：保留其他商家的加入结果，明确显示失败商家和原因。

## 6. 验收标准

- 页面初始状态说明需要健康档案，并能跳转完善。
- 生成成功后按三餐展示真实菜品，而不是只展示 Markdown 文本。
- 返回的每个菜品都能在菜品详情或菜品列表中找到。
- 替换菜品后，当前菜品、价格和营养汇总同步更新。
- 下架、缺货和不满足忌口的菜品不能被推荐或加入购物车。
- 跨商家加入购物车时，页面能明确展示商家分组及后续单独结算规则。
- 前后端接口方法、参数位置和响应结构一致。
- 前端构建通过，后端测试通过。
