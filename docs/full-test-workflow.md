# BiteSmart 全量测试工作流

本文档用于毕业设计/交付前的全量验收。目标不是只证明能启动，而是把后端、PC 前端、微信小程序、支付、实时定位、权限、数据一致性和非功能需求都按固定流程测到。

## 1. 测试分层

| 层级 | 目的 | 执行方式 | 通过标准 |
|---|---|---|---|
| 静态检查 | 提前发现语法、配置、页面结构问题 | `tools/run_full_test_workflow.ps1` 默认执行 | 无语法错误、无构建失败 |
| 后端自动化 | 验证核心 service/controller 行为 | Maven test | 测试全绿 |
| PC 前端构建 | 验证 Vue/TS/路由/组件可打包 | type-check + Vite build | 类型检查和生产构建通过 |
| 小程序静态检查 | 验证 app/page JSON、WXML 闭合、SCSS 结构、TS 语法 | `tools/check_pages.py` + `tools/ts_syntax_check.js` | 所有页面检查通过 |
| API 冒烟联调 | 验证登录、下单、计划、骑手、定位等主链路 | 启动后端后运行 smoke 脚本 | 每个 smoke 输出 PASS |
| 端到端人工验收 | 验证真实浏览器、小程序开发者工具、支付宝沙箱、定位授权 | 按矩阵逐项执行 | 关键流程截图/记录完整，无阻断缺陷 |
| 非功能验收 | 验证安全、性能、兼容、异常恢复、数据一致性 | 自动检查 + 专项手工测试 | 满足下方非功能标准 |

## 2. 一键基础检查

在项目根目录运行：

```powershell
.\tools\run_full_test_workflow.ps1
```

默认会执行：

- 后端 Maven 测试
- 数据库静态覆盖审计
- PC 前端类型检查
- PC 前端生产构建
- 小程序页面结构检查
- 小程序 TypeScript 语法检查

报告会输出到：

```text
outputs/test-runs/<时间戳>/report.md
```

如果后端已经连接好 MySQL/Redis 并运行在 `http://localhost:8080`，可以执行联调冒烟：

```powershell
.\tools\run_full_test_workflow.ps1 -RunApiSmoke
```

API 冒烟脚本依赖测试账号、测试数据和本地后端服务。建议先导入 `bitesmart.sql` 和必要增量 SQL，再启动后端。

## 3. 联调环境准备

### 后端

1. MySQL 创建 `bitesmart` 数据库。
2. 导入根目录 `bitesmart.sql`。
3. 如本地库不是最新状态，补跑 `docs/db` 和 `docs/sql` 下的增量脚本。
4. 启动 Redis。
5. 启动后端，确认 `/api` 可访问。

### PC 前端

1. 进入 `BiteSmart_front`。
2. 安装依赖。
3. 启动开发服务。
4. 确认代理指向 `http://localhost:8080`。

### 微信小程序

1. 用微信开发者工具打开 `BiteSmartMin`。
2. 开发者工具中可用 `localhost:8080`。
3. 真机预览时，需要把 `miniprogram/utils/request.ts` 中的局域网地址改成当前电脑 IP。
4. 勾选“不校验合法域名”仅用于本地调试；最终演示要按微信要求配置域名或使用合规代理。

### 支付宝沙箱

1. 使用本地环境变量或 IDE 运行配置注入支付宝参数。
2. 不要把真实密钥提交到仓库。
3. 支付回调地址必须能从支付宝沙箱访问，本地一般需要内网穿透。
4. 分别测试“模拟支付”和“支付宝沙箱支付”，两者验收口径不同。

## 4. 推荐执行顺序

1. 跑基础自动检查：`.\tools\run_full_test_workflow.ps1`
2. 启动 MySQL、Redis、后端、PC 前端。
3. 跑 API 冒烟：`.\tools\run_full_test_workflow.ps1 -RunApiSmoke`
4. 按 `docs/full-test-matrix.md` 做 PC 端页面验收。
5. 按 `docs/full-test-matrix.md` 做小程序开发者工具验收。
6. 用真机做登录、定位、配送轨迹、支付回跳等真实能力验收。
7. 做非功能测试：权限越权、异常输入、弱网、刷新恢复、并发下单、文件上传限制、日志与敏感信息。
8. 整理缺陷，按 P0/P1/P2 修复后回归。

## 5. 缺陷优先级

| 优先级 | 定义 | 例子 |
|---|---|---|
| P0 | 阻断主流程或造成数据/安全严重问题 | 登录失败、下单失败、支付状态错误、越权访问、ID 精度丢失 |
| P1 | 核心功能可用但体验或数据展示明显错误 | 订单详情字段为空、配送员信息缺失、统计值不对 |
| P2 | 不阻断流程，但影响完整性或演示观感 | 文案不统一、提示不清楚、边界状态缺少空态 |
| P3 | 优化项 | 包体过大、页面动画细节、局部样式微调 |

## 6. 非功能验收清单

| 方向 | 必测项 |
|---|---|
| 权限安全 | 未登录访问受保护接口返回 401；普通用户不能进管理员/商家接口；商家只能看自己的店铺/订单；骑手只能操作自己的配送任务；响应中不能出现密码哈希、密钥、私有配置 |
| 数据一致性 | 雪花 ID 前端全程按字符串处理；订单金额、支付金额、库存扣减、退款、结算流水一致；计划打卡同步饮食记录 |
| 异常恢复 | 后端重启后 token 处理正常；Redis 不可用时有明确错误；支付回调重复通知幂等；配送位置上传失败可重试 |
| 性能 | 首页、列表、订单查询、统计页在测试数据量下响应稳定；分页接口不一次性返回全量大数据 |
| 兼容 | PC 端 Chrome/Edge；小程序开发者工具和真机；不同屏幕尺寸下页面不遮挡、不溢出 |
| 可观测 | 关键操作有日志；错误响应结构统一；支付、订单、配送状态变化可追踪 |
| 数据隐私 | 本地密钥不进 Git；日志不打印密码、token、完整私钥；上传文件类型和大小受限制 |

## 7. 交付标准

项目可以进入最终演示/答辩前，至少需要满足：

- 自动检查全绿。
- PC 用户、商家、管理员三端核心路径跑通。
- 小程序用户、商家、骑手三端核心路径跑通。
- 一笔订单从下单、支付、商家接单、出餐、骑手接单、取餐、定位上传、送达、评价完整闭环。
- 支付宝沙箱至少完成一次发起支付、回跳、异步通知或人工模拟通知验证。
- 权限越权测试无严重问题。
- 所有 P0/P1 缺陷已关闭。
